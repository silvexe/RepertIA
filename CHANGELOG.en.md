# Change log

*Translation of [CHANGELOG.md](CHANGELOG.md); the Italian text prevails. Versions 2.14.0 and later are translated in
full; earlier versions are summarised (details in the Italian change log).*

For every version: what changes, how it was tested, what was not tested.

## 3.0.3 (in preparation)

**Reopening prepared cases.** Reopening a large case after closing the program took minutes: the counts, the Results tree and the Timeline chart were kept only in memory and were recalculated at every start. They are now also kept in the case cache (copies that can be rebuilt) and are valid until the case databases, the content of `case.json` or the program version change. The count of the Photos/Videos/Audio entry reread the metadata table for every audio file: rewritten, it gives the same number (on the iOS 17 test case 62,199, from 196 to less than 1 second); new cases also get an index on that table, prepared cases are not modified. The saved summary no longer expires when the LLM server is connected. Without an LLM server opening waited 3 seconds on Windows: the ports are now tried together (1 second). Measured on the iOS 17 test case (4.8 GB): reopening after restarting the program from over 4 minutes to about 2 seconds. The first calculation of the Results tree on that case still takes about 35 seconds.

**New version notice.** After updating, the notice kept appearing: the saved result of the last check ("version X is available") was not compared with the version in use, and stayed until the check was repeated. The saved result is now realigned with the program in use and, with the check at start, the check is repeated at once if the program has changed. One new acceptance-test check.

**Map: arrow keys.** Once a position was chosen, the point's popup took the keyboard focus and the arrow keys no longer moved through the list. Now ↑ ↓ (and ← →) move through positions and flights also after choosing a row or clicking on the map; with no position chosen, on the map the arrows still pan it.

Tested: acceptance test from sources on Windows 755/755 in Italian and English (128/128 on public images), navigation 525/525 in Italian and English. Not tested: the summary with an LLM server running; the arrow keys in the Flights tab.

## 3.0.2

**Logical source.** On the start page **🗂️ Logical source** opens a case from files already collected: zip, tar, tar.gz, 7z, rar, FTK Imager **AD1** logical images (also in several segments), ISO 9660 and UDF **CD/DVD** images (also BIN/CUE with 2352-byte sectors) or a folder. 7z and rar are opened with the program's 7-Zip in a derived copy; RAR 4 dates, in local time, are converted with the «Time zone of local dates» chosen for the case, which is stated. AD1 files are read with `dissect.evidence` 3.13 (Fox-IT, AGPL-3.0-or-later, new in the packages) and the MD5/SHA-1 written by FTK for each file are recalculated and compared (FTK's overall hash cannot be recalculated). Phone databases are recognised by name even outside the phone folder structure (chats and contacts, with a warning), iLEAPP/ALEAPP and WhatsApp backups are additional analyses, KML/GPX files become map layers. L01 files are not read (no public sample). Tested on public AD1 files (dissect.evidence tests and a segmented AD1: 8/8 hashes), 7z, zip, tgz, RAR 4 and 5, in Italian and English; new acceptance-test checks with embedded data.

**UDF with VAT.** CD-Rs written in several sessions (UDF with a virtual allocation table) are read neither by 7-Zip nor by Sleuth Kit: a RepertIA reader (ECMA-167, UDF 1.02-2.60, physical, virtual and metadata partitions) reads every VAT; files that exist only in previous VATs are under «[files only in previous VATs]» and counted as deleted. Tested on the «RM#3» CD-R of the NIST CFReDS «Data Leakage» case: the three final files, the 17 files of the previous VATs and the burning time (20:54-20:58 UTC) are those of the NIST answers.

**Windows: Search index, Internet Explorer, Sticky Notes, Google Drive.** New system artifacts: Windows Search index (`Windows.edb` of Windows 7, 8 and 10, with the compressed texts of Windows 7: files, Internet Explorer pages, mail with summary and attachments, Sticky Notes; the Windows 11 `Windows.db` is not read), Internet Explorer history (`WebCacheV01.dat`, times in UTC; IE downloads are not read), Sticky Notes (`StickyNotes.snt` and `plum.sqlite`, the latter without a real sample), Google Drive (`sync_config.db`, `snapshot.db` including deleted records and from shadow copies, `sync_log.log`), events 4608, 1100, 4634, 4647, 20001, 20003 and 133 (CD/DVD). New categories: Cloud services, Windows Search index, Notes. Tested on the PC of the NIST «Data Leakage» case: the 18 NIST answers checked (events, Google Drive, Search index, Internet Explorer, Sticky Notes) match; new acceptance-test checks with real values from the NIST index and the NIST `StickyNotes.snt`.

**Fixes found by comparing RepertIA with the NIST answers of the «Data Leakage» case.** All the questions of the case that are not pure reasoning were checked on the images of the PC, the USB drive and the CD-R. Seven defects or gaps came out, now fixed:
- **NTFS journal:** for a file renamed several times, every rename showed the previous name of the last rename. For example, `winter_whether_advisory.zip` appeared as «before: winter_whether_advisory.zip» instead of `[secret_project]_detailed_design.pptx`. Now every rename has its own previous name.
- **False extensions:** an Office document renamed `.amr` or `.svg` was not flagged. The AMR format is now recognised and SVG is among the known extensions: on the NIST USB drive the false extensions flagged go from 13 to 15 out of 17 (the other two match their content).
- **PST/OST mail:** the date is now the sending time, like the `Date` header; before, it was the delivery time, which Outlook records to the minute for sent messages. The delivery time stays in the message text.
- **Search terms:** those searched with Internet Explorer/Edge (Bing, Google, Yahoo, DuckDuckGo…) are extracted from the `WebCacheV01.dat` history, as already for Chrome and Firefox.
- **Installed programs:** there is now also the last write of the `Uninstall` key, which gives the installation time. `InstallDate` holds only the date.
- **Accounts:** there are now the creation date (last write of the name key in the SAM, as RegRipper does), the last failed attempt and the password date.
- **CDs with 2352-byte sectors:** for the derived 2048-byte copy, MD5 and SHA-1 are recorded too, the ones published by FTK Imager and NIST, and shown in the panel.

Two new acceptance-test checks, also tested the other way round: with the old code they give NO. Result of the verification in the Validation section.

**Security: three hardenings from CodeQL alerts.** GitHub's automatic analysis (Code Scanning) reported 104 points; checked one per category, almost all are false alarms (commands passed as lists without a shell, SQL with columns from a closed list and values as parameters, paths checked inside the case). Three points were hardened: on Windows the file and folder picker also doubles typographic quotes (‘ ’ ‚ ‛), which PowerShell treats as quotes, and on Mac typographic double quotes (“ ” „ ‟) that AppleScript may take as quotes; keys starting with `_` (internal to the server) are discarded from browser requests; the expression that strips tags from the HTML of mails and texts no longer slows down on texts with many `<` (before, the time grew with the square of the length).

**Windows: non-ASCII file names.** On Windows Sleuth Kit's `fls.exe` writes names in the system code page: Chinese, Japanese, Korean, Arabic, Hebrew, Russian or Hindi names became «??.txt» and names with accented letters or «ß» were altered too («Gef��.txt»), in the file list and in the timeline. Now, only on Windows and only when a line is altered, the real names of the partition are read with pytsk3 (the same Sleuth Kit, in UTF-8) and matched by record; names that are equal after the alteration are matched in directory order. Found with the NIST CFTT «Deleted File Recovery» DFR-04 images (names in about ten languages and scripts): after the fix all intact on NTFS, exFAT, FAT and ext.

**exFAT: fragmented deleted files recovered intact.** When a file is deleted exFAT frees the clusters only in the bitmap and leaves the chain in the FAT, but Sleuth Kit reads every deleted file as contiguous from the first cluster: a fragmented file came back with half of the sectors of another file (export, preview, hash). Now RepertIA reads the directory entry again and follows the chain in the FAT, only when it is certain that it is still the file's own (no NoFatChain flag, chain exactly as long as the size and terminated, distinct clusters all free in the bitmap, also for files left inside a deleted folder); otherwise Sleuth Kit's reading stays. Every reconstruction is recorded in the case log (`exfat_catena`, with the clusters read). NIST DFR-05 and DFR-12 exFAT images: 5 fragmented files out of 5 intact (before, 8 sectors out of 16).

**Deleted names with a reassigned inode.** When the inode of a deleted file has passed to another file (Sleuth Kit writes «(realloc)»), the content read is that file's and not the deleted one's: before, RepertIA showed it without saying so. Now the name is marked **DELETED · INODE REASSIGNED**, with the explanation in the preview, in the finding labels and in the portable report; the «deleted» filters include it. It applies to cases prepared with this version.

**ext3/ext4: files in deleted folders and leftover names.** On deletion a folder's inode loses its block pointers, but the block with the entries (name → inode) stays on the disk: Sleuth Kit does not find it and the files it held were left nameless or not listed (NIST DFR-11 and DFR-12: 21 files). Now RepertIA looks in the free blocks for folder blocks (entry «.» pointing to itself, then «..»), skipping the copies in the journal, and gives each file its path (`cartelle_ext` entry in the log; file systems up to 32 GB). Deleted names left without metadata are listed too, with inode 0 as Sleuth Kit does: on ext the name whose inode number was covered by a new entry, on exFAT the name entry left over when a new file reused the first entries of the set (`exfat_nomi_residui`). On the NIST DFR images: no open assertion (835: 643 OK, 179 known limits, 13 cases where the image differs from the NIST reference).

**Carving of graphic files not aligned to sectors.** PhotoRec looks for the start of files only at the start of each sector: an image starting in the middle of a sector (inside a document, in a stream copied byte by byte) was not found. Now, after PhotoRec and in the same space, RepertIA looks byte by byte for JPEG, PNG, GIF, BMP, TIFF and HEIC/HEIF and works out the end from the structure of the format (JPEG segments up to EOI, PNG chunks with CRC, GIF blocks, checked BMP header, TIFF IFDs, HEIC boxes): a candidate that does not close is discarded. Files already recovered by PhotoRec are skipped and, on the partition of a raw image, so are allocated blocks; the EXIF thumbnail is extracted from JPEGs too. Files in `carving/photorec_p<offset>/non_allineati` (`carving_non_allineati` entry in the log; `REPERTIA_CARVING_BYTE=0` to switch it off). NIST CFTT images: not aligned 47 out of 47 (2014 set) and 36 out of 36 plus 3 thumbnails (2023 set), from 0, no false positives; on a USB stick of the NIST «Data Leakage» case 8 more real images.

**Carving: PhotoRec default file types.** RepertIA switched on every type («everything»), including the signatures the PhotoRec author leaves off because they are noisy: on the 8 NIST CFTT graphic carving images hundreds of false «gsm» files split BMP and TIFF files (39 complete out of 47). Now the default types are used, as in the NIST tests (47 out of 47; `REPERTIA_PHOTOREC_TIPI=tutti` to switch them all on), and whole EXIF thumbnails of photos that PhotoRec discards because fragmented are kept too. Comparison with the 9 tools of the CFTT reports in VALIDATION.

**exFAT: dates with the UTC offset.** exFAT entries can hold, next to the time, the UTC offset of whoever wrote the disk (Windows, macOS). Sleuth Kit returns the time without applying it and RepertIA added the device time zone: on the NIST DFR-01 exFAT image the dates were 9 hours ahead (the same error the CFTT reports find in EnCase and ILooKIX). Now, when the offset is written in the entry, the UTC instant is the disk time minus the offset (timeline and metadata tab); the device time zone remains only for entries without an offset (cameras and other devices). Dates of cases already prepared change only when they are redone.

**Deleted files with reused blocks.** A deleted file whose data blocks are now assigned to another file returns, at least in part, that file's content: it is now marked **DELETED · BLOCKS REUSED** (preview, finding labels, portable report). All the blocks RepertIA reads are checked (the exFAT chain too), with the file system allocation maps read once per partition: NTFS $Bitmap, FAT cluster table, exFAT bitmap, ext group bitmaps (`cancellati_blocchi_riusati` entry in the log). On the NIST CFTT images all the objects with data of active files are declared.

**ext: files in deleted folders.** On ext2 the files left inside a deleted folder did not appear: Sleuth Kit 4.15 no longer puts them among the orphans (3.2.2 did). Now the deleted inodes with a size that no name lists are taken from `ils` and added as `$OrphanFiles/OrphanFile-N` (`orfani_ext` entry in the log). Both found by comparing RepertIA with the NIST CFTT reports.

**NIST CFTT «Deleted File Recovery» validation.** The 90 public DFR-01…17 images NIST uses to test deleted-file recovery: 835 assertions, 643 equal to the reference, 179 known and explained limits (ext3/ext4, fragmented files on FAT, HFS+), 13 where the raw image differs from the NIST reference, none open. Four of these images (NTFS, non-ASCII names, fragmented exFAT) are now in the acceptance test, with the expected values taken only from the NIST document. Comparison with the NIST CFTT reports on FTK, EnCase, X-Ways, ILooKIX, SMART and TSK/Autopsy on the same images: for complete and correct files RepertIA is first or level with the first on FAT, exFAT, NTFS and ext; on exFAT the only one to recover them all (273/273 and 376/376). On the other items of the reports (active files and folders of DFR-16 and DFR-17, MAC times, non-Latin names, Recycle Bin, compressed NTFS and files inside the MFT) RepertIA is complete and correct everywhere; on exFAT dates only X-Ways and RepertIA. Details in VALIDATION §2 and §3.

**Windows: shifted archive dates.** On Windows 7-Zip ignores the given time zone and writes dates in local time with the PC's current offset: 7z, RAR 5, ISO and UDF dates were one hour ahead in Italy in winter (two in summer). The offset is now removed; RAR 4 (DOS time) is unchanged. Found by the first acceptance test run on Windows; tested on 7z, RAR 4 and 5, UDF and ISO.

**Linux: installation.** A tester on Debian 13 reported Poppler and bulk_extractor not active. `installa.sh` asked apt for `libewf-tools`, a package that exists in neither Debian nor Ubuntu (it is called `ewf-tools`): apt refused the whole list, Poppler included. The name is now right, packages the distribution lacks are listed at the end and do not block the others, and `aggiorna-strumenti.sh` updates only the installed ones. bulk_extractor is not a Debian or Ubuntu package: README_EN explains how to build it and where to put it (PATH or `strumenti/bulk_extractor/`). When a tool is missing the program on Linux suggests the `apt` command and no longer `brew install`. Tested with a simulated apt without bulk-extractor; **not tested on a real Linux**.

**Tests against public reference data.** RepertIA was compared with the NIST CFTT images, the NIST CFReDS "Data Leakage" case and Joshua Hickman's Android 14 and iOS 17 smartphones: results in `docs/prove/`, measuring scripts in `tools/prove/`, summary in the README.

**Fixes of 9 November** (found with the smartphone tests and in use):
- **iMessages in "Recently Deleted":** a message deleted less than 30 days earlier stays in `sms.db`, and RepertIA showed its text without saying it had been deleted. It is now marked "deleted by the user" with the date of deletion (`chat_recoverable_message_join` table), in the chat view, in the deleted filter, in the report and in the notes for the agent. Found on Hickman's iPhone; new acceptance-test check, one for each of the six smartphone cases.
- **iLEAPP/ALEAPP artefact titles:** long titles and values were cut without any sign; the cut is now marked with "…".
- **Report on disk cases:** the report dialog gave "no such column: grp" on cases prepared before that column existed; it now checks for it.
- **HTML report:** navigation bar always visible with previous and next section, button to go back to the top, table header aligned with the columns.
- **AD1 with files without data:** FTK can list files whose content it did not copy; reading used to stop with an error. They are now reported as "without data" in the verification box and in the log, and the analysis goes on.
- **PhotoRec on Windows:** with the case folder on a different drive from the program, PhotoRec did not find its terminfo database and recovered nothing, without errors. The path is now passed in the form it understands (`/cygdrive/…`).

**Acceptance test.** The test data include the RM#3 CD-R of the NIST CFReDS «Data Leakage» case (public domain, unmodified, SHA-1 published by NIST and checked), with the expected values taken from the official NIST answers (questions 34, 56, 57, 59). From sources on Windows: 748/748 checks in Italian and English (128/128 on public images), navigation 525/525.

## 3.0.1

**Illustrated report: whoever receives it relives the case.** **Report** opens a window where you choose what goes into it: the sections (case and image data, analyses performed, findings, bookmarks timeline, methodological notes, environment and log, full text), the Bookmarks categories (**Choose items…** removes single items) and, if needed, **whole types**: all chats, all photos, all videos, all audio, all email, the artifacts of a category or of an iLEAPP/ALEAPP section, all map locations. Every item is shown as in the case: photo thumbnails (a click opens the original, copied to the report folder with its SHA-256; for HEIC, TIFF and RAW also a large JPEG version), videos with a frame, documents with their first page, **chats with bubbles, sender, time, source (table and row) and attachments** (photos shown, videos with a frame, other files listed as in the conversation, transcripts), artifacts and email with all their fields. The result is an `export/report_<date>/` folder with **report.html** (split into pages, it copes with “all photos” of a phone), **report.pdf** and, if chosen, **report.docx** with the same content, plus `impronte.csv` with the SHA-256 of every file; everything is in the case log. The PDF embeds a Unicode system font (Arial on Mac and Windows, DejaVu on Linux) with only the glyphs used: chats in Cyrillic, Greek or Chinese are readable; Arabic and Hebrew appear with unjoined letters and left to right (they are correct in the HTML report). PDF and Word carry at most 5,000 previews and 20,000 table rows; beyond that, the rest is in the HTML report. “Text only (report.md)” keeps the previous report. The **New report of the portable report** now also shows Bookmarks chats as conversations with their attachments, and the portable report includes the attachments of bookmarked chats and a frame for every video. Tested on the iOS test case (chat with HEIC and JPEG photos, 32 messages), on DFTT 8 and DFTT 11 (photos recovered by carving), in Italian and English; new acceptance-test checks.

**Transcriptions reviewed and confirmed by the analyst.** Under the automatic transcription, in the audio preview and in the chat: **✏️ Correct the transcription** (or **Write the transcription** when there is none) opens the text to edit while listening; **Save as draft** or **Save and confirm** (with operator and an explicit confirmation). The automatic transcription does not change: each save is a separate version with operator, date and SHA-256 of the text, in the case log. The analyst's text is searchable; confirmed audio files are under Photos/Videos/Audio › Audio › **✅ Confirmed transcriptions** (next to **📝 Transcribed, to be confirmed**), in the **Confirmed transcriptions** Bookmarks category (the chat message, so also in the report) and in the chat export. Tested in the browser in Italian and English on the test case with the public recordings.

**Transcription model: sturdier download.** An interrupted download resumes where it stopped (up to 5 times); if the file received is not the model, the message says why: a web page instead of the model (proxy, network filter, antivirus), an incomplete download or an altered file, with both hashes, and the event goes to the diagnostic logs. Checked again on 04/11/2026 by downloading the three models: hashes equal to the list. Tested with a fake server (web page, two interruptions, correct file).

**Transcription model: hash checked online or typed by hand.** Before downloading, RepertIA reads from Hugging Face the SHA-256 declared for that file (also by itself when the models window opens, with no case open: the *Expected SHA-256* line shows the hash read online, with the size, and below it whether it is the same as or different from the one in the list; if it has changed the download goes ahead with the new one and “I already have the model file…” also accepts the file with the hash read online, without typing it) and compares the downloaded file with it; if it differs from the program's list, the model record and the log say so. For a file brought from another computer without network access, the SHA-256 given by the source can be typed: the file is accepted only if the computed hash is the same, and the record keeps who compared it. Checked on 04/11/2026: the SHA-256 values declared by Hugging Face for the three models are still those in the list and downloading from the program works; what the site now shows next to the files is the Xet identifier, which is not the file's SHA-256.

**Chats: the two searches are separate.** The search in the conversation list (left) is no longer copied into the “Search in the conversation” box, which used to hide the messages when searching for a name or number. The conversation box now also finds the sender's name and number, as well as the text. Tested in the browser in Italian and English on Hickman's Android 14 (Facebook Messenger name, WhatsApp number).

**Import notices in the menu bar.** “⚠ Import notices (n)” is next to “AI model”, no longer at the bottom of the case pane.

**Audio in MP4 containers.** .m4a recordings (and voice notes without an extension) with a generic MP4 header were counted as videos: now the track read in the file (audio or video) decides. With the fix: Android 14 344 videos and 223 audio files, iOS 17 636 videos and 3,716 audio files.

**Windows.** Preview, chats, database manager, map, guide and full-screen Timeline open in windows like the computer's: they move by the title bar, resize from edges and corners, — minimises them to the **Open windows** bar at the bottom (one click reopens them), ⤢ or a double-click on the title makes them full screen, ✕ closes them; the last one touched is in front. You can work on the case with the windows open, and several databases can be open together. The preview normally stays in the right-hand pane: ⧉ opens it in a window (choice remembered) and ⧉ in the window docks it back; 📌 copies its content into a separate window, to compare several files. Position and size are remembered per kind of window; “Reset interface” clears them. Esc closes only the window in use. Windows stay inside the browser page.

**Date format.** 📅 menu next to the time zone: day/month/year (default in Italian), ISO year-month-day (default in English), month/day/year or month in letters; it applies to tables, previews, chats and the portable report. Only the display changes: data, log, CSV files, filters and sorting stay in ISO format.

**Photos, videos and audio: all of them, by app.** On phones, indexing now recognises photos, videos and audio by their content (the first bytes of each file), not only by extension: app caches with names without an extension or with their own extensions (“.0”, “.cnt”, “.exo”…) are included. Each file is assigned to the app or folder it belongs to (Android package, iOS container, Camera/DCIM, Download…): under Photos, Videos and Audio there is an entry for each one, with “of which in caches”, and the filters “App or folder” and “Only from app caches”. In the list, under the name, the app, cache and recognised format; previews and thumbnails work without an extension too. Tested on Josh Hickman's public images: **Android 14** 21,295 photos (8,653 by extension), 344 videos (92), 223 audio files (190), 10,177 files in caches, 81 apps and folders, 56 seconds; **iOS 17** 57,663 photos (45,905), 636 videos (456), 3,716 audio files (3,492). Cases already prepared are updated by running the additional analysis “Text and media” again.

**Photos, videos and audio by content on storage media too.** The same recognition applies to disks, pen drives and forensic images: a JPEG without an extension or with a wrong one (browser caches, renamed files) goes into Photos. A deleted file goes in by content alone only if the content read is still its own (record not reassigned, cluster not overwritten); with the extension of a media format it goes in anyway, as before. Under Photos, Videos and Audio there is an entry for each program or folder (Chrome, Edge, Firefox, Safari, Telegram…, Pictures, Desktop, Downloads, Temporary files, Recycle bin, Programs, System) and one for **Recovered by carving**; filters “Program or folder” and “Only from caches”. Tested on DFTT 8 (NTFS): `alloc/file2.dat` (JPEG with a .dat extension) and the deleted `del2/file7.hmm` are now among the photos; on a FAT image built with 40,000 files, 21 seconds. New acceptance-test checks on the disk cases. Cases already prepared are updated by running “Text and media” again.

**Photos and videos inside browser caches.** Chrome, Samsung Internet, Edge, Opera, Brave, DuckDuckGo and apps that show web pages (WebView) store downloaded images in Chromium's “Simple Cache”: each entry (`Cache_Data/<hash>_0`) starts with a header and the web address, and the actual photo comes after, so it was not recognised from the first bytes. Indexing now reads the entry according to Chromium's format, finds where the content starts and ends and, if it is a photo or a video, extracts it among the extracted files (read-only, MD5/SHA-1/SHA-256) with the name taken from the address and the extension of the real format (“a.png” containing a JPEG becomes “a.png.jpg”). It works for phones and storage media. The photos go into Photos/Videos under the browser or app (“Samsung Internet · cache”…), with the entry's date, metadata and thumbnail; the preview shows the web address and the offset of the content in the source file, **Container** opens the cache entry; full list in Archives and attachments › **Browser caches**; in the illustrated and the portable report with origin, offset and hashes. A new indexing keeps the same numbers for the extracted files (Bookmarks and perceptual hashes stay valid). Tested on entries built with the format published in Chromium's source code (24- and 20-byte header, truncated entry, HTML page that must not go in), on an Android extraction and on a FAT disk with Chrome and Edge caches; new acceptance-test checks. On Hickman's public Android 14 (Pixel 7a): the 11,256 cache entries yield 4,219 photos and 7 videos (none before), from Imgur, Chrome, Edge, Google apps, Gmail, Opera, Brave, DuckDuckGo and two photo-hiding apps (Gallery Vault, a “calculator”); the other entries are pages, scripts and data. Independent check on 30 random entries re-read from the extraction zip: the bytes at the stated offset are identical to the extracted file (SHA-256). 4,214 images open; 5 tracking GIFs are already incomplete in the server's response. Time for the whole photo, video and audio indexing: 48 seconds.

**“Text and media”.** The additional analysis “Text and metadata” is now called **Text and media**: besides the text of documents it recognises photos, videos and audio by content (in app and browser caches too) and reads their metadata. Cases already prepared are updated by running it again.

**The AI agent sees the same data as the interface.** Before 3.0.1 some case data was shown in the interface but did not reach the agent: now extracted files (including **photos and videos from browser caches**, with the source web address) and **anomalies** (for example a BitLocker volume) are available whenever the case contains them, even without the “archives” or “anomalies” additional analyses; two new tools, `count_media` and `list_media`, count and list **photos, videos and audio recognised by content** by app, program or folder, type and area (app, cache, shared storage); under every message the agent reads there are the **time it was read on this phone** (received messages) and the **delivery and read receipts** (sent messages) with their source and “meaning not verified” where it applies, and the prompt reminds that a missing “read” does not prove the message was not read. Keychain passwords stay excluded, as before. Tested on the test cases (web cache on Android and on a disk, iOS with 22 receipts, BitLocker) in Italian and English; new acceptance-test check: every type of data present in the case has its tool.

**ExifTool 13.61 in the Windows packages.** Instead of 13.60: it fixes a hang on a corrupted FLIF file and excessive memory use with corrupted metadata, useful with deliberately crafted evidence. Checksums of the zip and of the sources equal to those published on exiftool.org. Tested: the two versions give the same metadata, field by field, on 2,284 test files (photos, videos, audio, PDFs, documents) of the acceptance test and the demo cases. On Mac and Linux ExifTool comes from Homebrew and apt, as before.

**WhatsApp calls: number, name and outcome.** In recent WhatsApp calls the contact is often the **LID**, WhatsApp's anonymous identifier: the Contact column now shows the **number** WhatsApp recorded for that LID (never inferred) and the **address-book name**, with the LID below. The same LID calls also go into the number's **chat**: before they were left out, and fewer WhatsApp messages were counted than by other programs. Under WhatsApp and WhatsApp Business the calls are split into **Answered**, **Not answered** (`call_log` code 2: missed incoming and unanswered outgoing) and **Rejected** (code 4), each with **Voice** and **Video**. Codes 2 and 4 come from comparing a real case with another program (same totals per outcome): there is no public documentation and the public test data only has answered calls (code 5). New acceptance-test check with a test database.

**Tree totals and filters.** The number next to **Photos/Videos/Audio** only counted the files with metadata, without audio: it now includes photos, videos, audio and the new **Other files with metadata** subsection (PDFs, documents), and the entry opens exactly those files (also in the portable report). In the date filters, typing the year by hand sent the cursor back to the day at every digit: the filter is now applied once the year is complete. ## 2.18.1

Reliability fixes for the NTFS journal and event logs. **NTFS journal: paths with the sequence number.** An operation's folder was looked up by MFT record number only: if that record had been reused by another folder, the file ended up in the wrong folder (a plausible but false path). Now the reference is complete (record and sequence): the current MFT path is used only if the record is still that folder (same sequence, or increased by 1 if the record is free); otherwise the name recorded in the journal for that reference is used, otherwise "MFT folder n sequence s: record later reused by …". For the same record, an existing entry wins over a deleted one. **Journal: limit and status stated.** Above 500,000 operations the most recent are kept and the new system entry "NTFS journal $UsnJrnl read" says how many, the period, how many were excluded and how many folders have a reused record or an unverifiable sequence; a missing (disabled) or unreadable journal is stated ("NTFS journal missing" / "not read") instead of silently giving zero operations. **Event logs: recovered and unreadable records.** Records recovered from the free space of the .evtx file are marked "recovered" (title, detail and `recuperato` field); those identical to an active record are not counted twice (previously a logon could be counted twice); unreadable records are counted. The account card says how many logons and sessions come from recovered records; each log read has a system entry with active, recovered and unreadable records, and for system events also the 20,000 limit if reached; logs not extracted or unreadable and a missing pyevtx module are stated. **Tested:** built journal (v2 records with current folder, reused folder known and unknown to the journal, deleted folder not reused, limit, unverifiable sequence; missing journal and volume that cannot be opened) and simulated libevtx (active, recovered, duplicate recovered, unreadable records) with logons and system events. **Not tested:** real pytsk3 (`open_meta(...).info.meta.seq`) and real libevtx on a disk: re-run "Artifacts" on a real image and compare with MFTECmd / EvtxECmd.

## 2.17.3

Two fixes after a second test on the same real image. **Anomalies: false positives remained among deleted files.** The 2.17.2 check only looked at whether the first cluster was currently assigned to an existing file; but if after the deletion those clusters were used by another file, itself deleted, they are free and the content read belongs to that other file (an `msedge.dll` that "contains" a JPEG, an `image.pdf` that "contains" an executable). Now a single pass over the MFT finds every other record (free ones too) using those clusters, and the content must be consistent with the file's size and ending; if it is not, the entry is excluded and the summary says how many and why. On the real image: of the 293 reports on deleted files 12 remain, almost all of low severity. Also, program modules with their own extension (`office.odf`, Acrobat's `Flash.mpp`…), executables in program folders, installer icons and registry logs are no longer anomalies; a photo/video swap is low severity. **User accounts: logons at 0.** For an account linked to a **Microsoft account** (or signing in with PIN/Windows Hello) Windows does not update the SAM logon counter and date. Logons are now counted from the event logs: `Security.evtx` (4624 successful, by type: interactive, cached credentials, remote; 7 = unlocks, counted separately; the two events an administrator generates for the same logon count once; 4625 failed) and `System.evtx` (Winlogon 7001, sessions). The account card shows the number of logons in its title, the period covered by the logs (earlier logons are no longer recorded), the last logon, the Microsoft account address and the SID; the SAM counter is still shown separately.

## 2.17.2

Three fixes after use on a real image. **Anomalies: false positives.** A `.png` could turn out to be a "Windows executable": for a *deleted* entry the program read the content from the inode number, but on NTFS (and FAT, ext) that record may already have been assigned to another file, or its clusters overwritten. Now, before reporting a deleted file, it checks that the name matches the one stored in the record and that the first data block has not been reused; entries no longer reliable are excluded (the number is in the summary). Files with a current name are examined first, so an inode already read is not read again under an old name. More known executable extensions (`.msstyles`, `.xll`, `.vxd`…), no anomaly for a different format in `.dat/.bin/.db/.tmp…` and low severity for a swap between image formats. **User accounts: logons always 0.** Windows writes registry changes first to the log files (`SAM.LOG1`, `SAM.LOG2`, `NTUSER.DAT.LOG1`…) and only occasionally to the hive: reading `SAM` alone shows an old state. Now the logs next to the hive (SAM, SYSTEM, SOFTWARE, NTUSER.DAT, Amcache) are applied to a **working copy** (records verified with Marvin32 hashes, only if the sequence is continuous; the original does not change) and the operation is stated among the artifacts ("Registry: logs applied to…"). Moreover the SAM counter does not count all logons (Microsoft account, PIN, Windows Hello): if it is 0 but the account has been used, "never logged on" is no longer written, and the last profile load and unload (SOFTWARE, ProfileList), the bad passwords and, for each user, the last write of `NTUSER.DAT` are added. **Documents by extension**: in the tree view the Documents entry is split by extension, with an *Extension* filter in the section.
