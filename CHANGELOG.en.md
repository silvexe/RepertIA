# Change log

*Translation of [CHANGELOG.md](CHANGELOG.md); the Italian text prevails. Versions 2.14.0 and later are translated in
full; earlier versions are summarised (details in the Italian change log).*

For every version: what changes, how it was tested, what was not tested.

## 2.21.0

**Bookmarks:** an **Open chat** button on a chat's record; the whole chat in the bookmark export (HTML, CSV, attachments, optional period) and in the report; **Bookmark timeline** in order of event date, also in the report and as CSV. **Link forensic copy** in the Case menu: a case moved to another computer finds its copy again, accepted only with the same SHA-256, with a log entry. **Export diagnostic logs** (new technical log, no case data, mandatory preview). **iLEAPP/ALEAPP:** limit raised from 500,000 to 2,000,000 rows and, beyond it, small tables before huge ones: on a test iOS 17 iPhone 20 of 21 million rows are FSEvents, which took the room of the others. New script `tools/controlla_versioni.py`. **Tested:** acceptance test 448/448 in Italian and English from the Mac package, 77/77 on public images (11 new checks: bookmarked chats, timeline, report, export with period, Link forensic copy, diagnostic logs); browser test on test cases. Acceptance test on Windows with the final package passed (reported by the author). **Not tested:** Linux; the row limit on a real report above 2 million with the timing of the new import.

## 2.20.3

**Fixes for WhatsApp on Android.** **`msgstore.db` not read:** with the error `'int' object has no attribute 'find'`, a defect stopped the whole database being read when an attachment followed a call in a chat. It affects Mac, Windows and Linux from 2.20.0 onwards: if the notices of a case show `msgstore.db: not read`, the chats read by RepertIA are missing. Simply re-read the case: **Additional analyses → Chats and address books**. **crypt15 backups:** they are now decrypted with `com.whatsapp/files/encrypted_backup.key`, if it is in the extraction, or with the 64-digit key given by the analyst, which stays in memory only. Earlier manuals and guides said the crypt15 key is not on the phone: that was wrong. *Tested:* acceptance test 437/437 in Italian and in English on the Mac and 437/437 on Windows 11 with the fixes; a real public crypt15 with the key in the file, typed, missing or wrong and with an altered byte; on the public Android 14 image the same result as before, row by row. *Not tested:* a crypt15 with real messages, the final Windows package, the Linux package. The defect was reproduced on constructed data: the Android 14 image does not show it.

## 2.20.2

**Fix for smartphone cases on Windows.** On Windows, iLEAPP ends the lines of its TSV files with a double line break and RepertIA imported an empty row after every real row: each table of N rows became 2N+1 (e.g. 333 → 667). Smartphone cases prepared **on Windows** with 2.20.1 therefore have empty rows in all iLEAPP artifacts, inflated counts, searches and reports, and **non-existent calls** may appear. Mac and Linux are not affected, nor is ALEAPP (Android). Empty rows are now ignored and, when a case with this defect is opened, RepertIA shows a warning: **the case is not changed and must be redone**, and so must any reports. iLEAPP source paths are always cited with `/`. The acceptance test checks that no empty rows enter the case, also with a TSV written as on Windows. *Tested:* acceptance test 433/433 in Italian and in English on the Mac and 433/433 on Windows 11 with the final package. *Not tested:* the Linux package.

## 2.20.1

**AI Act compliance (Regulation (EU) 2024/1689).** **Agent findings**: in `findings.json` every finding recorded by the agent carries `"origine": "modello IA"` (AI model), the model name, the server and `"stato": "da verificare"` (to be checked); those written with *Record finding* are "entered by the analyst"; those of earlier cases "origin not recorded". The findings box shows the origin label and the **✓ I confirm, verified** button, which records operator and date in `findings.json` and in the hash-chained log (`finding_verificato`). In the reports (Markdown, Word, PDF, portable) every finding carries "Generated by AI model (*name*) – to be checked" or "Verified by *operator* on *date*"; the sentence "Every finding was verified by the analyst on the forensic tools" only if all of them are, otherwise how many are verified and how many are not; the Word and PDF metadata say "contains text generated by an AI model" with the keyword "AI-generated content". **External LLM server**: an address that is neither on this computer nor on the local network (private IPs 10.x, 172.16–31.x, 192.168.x, local IPv6, names without dots or with `.local`, `.lan`, `.internal`…) asks for an explicit confirmation before use, which is recorded in the case and in the log; the report says "external server indicated by the analyst: *address*" instead of "internal network, without external services"; an unconfirmed external server is not connected automatically when a case opens. **Chat**: under every answer "Answer generated by an AI model (*name*): hint to be checked" (also on the command line). **OCR**: "automatic OCR text" in the document list and a warning in the report (transcriptions were already "automatic transcription"). New **AI_ACT.md** and **AI_ACT.en.md** (intended purpose, excluded uses, assessment under Article 6(3), Article 50 obligations, note for offices: deployer, Italian Law 132/2025, impact assessment, human oversight, Article 25; not legal advice), linked from the README. Acceptance test +5 checks (agent finding "to be checked" in findings.json and in the report, Word and PDF metadata, verified with operator and date after the confirmation also in the log, local/private and external servers): **427/427 in Italian and English** (178 disk + 249 smartphone), from the sources and from the Mac package; navigation test 66/66; interface tested in the browser (labels, confirmation with operator, external-server warning cancelled and confirmed). **Not tested:** Windows and Linux of the rebuilt packages; a real external LLM server (tested with an address that does not answer).

**iOS keychain through iLEAPP (before publication).** The new smartphone case form and, for an existing case, the case panel have the optional field **«Keychain – file acquired separately, e.g. GrayKey»** (iPhone only). **Navigation after a Search, horizontal dividers and top bar (last fixes before publication).** On the iOS 13.4.1 case, after a search from the **🔎 Search** button, *← Back* seemed not to work and clicks in the tree changed the breadcrumbs (e.g. «System artifacts › … › Accounts») but not the content (the Timeline stayed); on the results the breadcrumbs said «Documents». Main cause (found with the Console error after the first round of fixes): in the Results tree the check of the items to keep open (`renderResTree`) assumed that every item had sub-items; the saved searches under «🔎 Search», the Bookmark categories and the «Open tabs» have none, and with the parent item closed (▸) every change of section stopped with a JavaScript error after updating section and breadcrumbs and before loading the table (defect of 2.20.0, absent in a private window because there the tree starts with «Search» open). ## 2.18.1

Reliability fixes for the NTFS journal and event logs. **NTFS journal: paths with the sequence number.** An operation's folder was looked up by MFT record number only: if that record had been reused by another folder, the file ended up in the wrong folder (a plausible but false path). Now the reference is complete (record and sequence): the current MFT path is used only if the record is still that folder (same sequence, or increased by 1 if the record is free); otherwise the name recorded in the journal for that reference is used, otherwise "MFT folder n sequence s: record later reused by …". For the same record, an existing entry wins over a deleted one. **Journal: limit and status stated.** Above 500,000 operations the most recent are kept and the new system entry "NTFS journal $UsnJrnl read" says how many, the period, how many were excluded and how many folders have a reused record or an unverifiable sequence; a missing (disabled) or unreadable journal is stated ("NTFS journal missing" / "not read") instead of silently giving zero operations. **Event logs: recovered and unreadable records.** Records recovered from the free space of the .evtx file are marked "recovered" (title, detail and `recuperato` field); those identical to an active record are not counted twice (previously a logon could be counted twice); unreadable records are counted. The account card says how many logons and sessions come from recovered records; each log read has a system entry with active, recovered and unreadable records, and for system events also the 20,000 limit if reached; logs not extracted or unreadable and a missing pyevtx module are stated. **Tested:** built journal (v2 records with current folder, reused folder known and unknown to the journal, deleted folder not reused, limit, unverifiable sequence; missing journal and volume that cannot be opened) and simulated libevtx (active, recovered, duplicate recovered, unreadable records) with logons and system events. **Not tested:** real pytsk3 (`open_meta(...).info.meta.seq`) and real libevtx on a disk: re-run "Artifacts" on a real image and compare with MFTECmd / EvtxECmd.

## 2.17.3

Two fixes after a second test on the same real image. **Anomalies: false positives remained among deleted files.** The 2.17.2 check only looked at whether the first cluster was currently assigned to an existing file; but if after the deletion those clusters were used by another file, itself deleted, they are free and the content read belongs to that other file (an `msedge.dll` that "contains" a JPEG, an `image.pdf` that "contains" an executable). Now a single pass over the MFT finds every other record (free ones too) using those clusters, and the content must be consistent with the file's size and ending; if it is not, the entry is excluded and the summary says how many and why. On the real image: of the 293 reports on deleted files 12 remain, almost all of low severity. Also, program modules with their own extension (`office.odf`, Acrobat's `Flash.mpp`…), executables in program folders, installer icons and registry logs are no longer anomalies; a photo/video swap is low severity. **User accounts: logons at 0.** For an account linked to a **Microsoft account** (or signing in with PIN/Windows Hello) Windows does not update the SAM logon counter and date. Logons are now counted from the event logs: `Security.evtx` (4624 successful, by type: interactive, cached credentials, remote; 7 = unlocks, counted separately; the two events an administrator generates for the same logon count once; 4625 failed) and `System.evtx` (Winlogon 7001, sessions). ## 2.17.2

Three fixes after use on a real image. **Anomalies: false positives.** A `.png` could turn out to be a "Windows executable": for a *deleted* entry the program read the content from the inode number, but on NTFS (and FAT, ext) that record may already have been assigned to another file, or its clusters overwritten. Now, before reporting a deleted file, it checks that the name matches the one stored in the record and that the first data block has not been reused; entries no longer reliable are excluded (the number is in the summary). Files with a current name are examined first, so an inode already read is not read again under an old name. More known executable extensions (`.msstyles`, `.xll`, `.vxd`…), no anomaly for a different format in `.dat/.bin/.db/.tmp…` and low severity for a swap between image formats. **User accounts: logons always 0.** Windows writes registry changes first to the log files (`SAM.LOG1`, `SAM.LOG2`, `NTUSER.DAT.LOG1`…) and only occasionally to the hive: reading `SAM` alone shows an old state. Now the logs next to the hive (SAM, SYSTEM, SOFTWARE, NTUSER.DAT, Amcache) are applied to a **working copy** (records verified with Marvin32 hashes, only if the sequence is continuous; the original does not change) and the operation is stated among the artifacts ("Registry: logs applied to…"). Moreover the SAM counter does not count all logons (Microsoft account, PIN, Windows Hello): if it is 0 but the account has been used, "never logged on" is no longer written, and the last profile load and unload (SOFTWARE, ProfileList), the bad passwords and, for each user, the last write of `NTUSER.DAT` are added. **Documents by extension**: in the tree view the Documents entry is split by extension, with an *Extension* filter in the section.

## 2.15.3

**Correct FAT/exFAT dates on Windows too**: on Windows Sleuth Kit did not understand the name of the device's time zone (e.g. `Europe/Rome`) and applied "zone 0 with US daylight saving time": FAT/exFAT dates were shifted by one hour (DFTT 5 test on the Windows PC: 2 checks failed). Now Sleuth Kit always reads the time written on the disk as it is (neutral zone `UTC0`, understood the same way by Windows, macOS and Linux) and RepertIA converts to the device's time zone with the time-zone database (exact European daylight saving time, in past years too). This applies to the timeline, tree, Metadata tab and portable report; NTFS/ext/HFS/APFS dates (already UTC) do not change. Cases with FAT/exFAT partitions prepared on Windows with versions 2.13.7-2.15.2 are recomputed automatically when first opened (`date_fat_ricalcolate` entry in the log).
